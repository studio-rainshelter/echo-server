# EchoServer Constitution

## Core Principles

### I. 간결성과 가독성 우선 (Simplicity & Readability First)

**원칙:**
- 모든 코드는 간결하고 읽기 쉬워야 한다 (MUST)
- 주석은 최소화하고 코드가 자체 설명되도록 작성해야 한다 (MUST)
- YAGNI(You Aren't Gonna Need It) 원칙을 준수해야 한다 (MUST)
- 복잡한 추상화보다 명확한 구현을 선호해야 한다 (SHOULD)

**근거:** 에코 서버는 개발 및 테스트 도구로 사용되므로, 코드의 명확성과 이해 가능성이
기능의 복잡성보다 우선되어야 한다. 유지보수성과 협업 효율성을 극대화한다.

### II. 최소 의존성 (Minimal Dependencies)

**원칙:**
- 불필요한 라이브러리 사용을 금지한다 (MUST NOT)
- 새로운 의존성 추가 시 명확한 근거가 필요하다 (MUST)
- 핵심 기능은 표준 라이브러리로 구현 가능한지 먼저 검토해야 한다 (MUST)
- 의존성 추가 시 번들 크기와 보안 영향을 평가해야 한다 (MUST)

**근거:** 의존성 최소화는 보안 취약점 노출을 줄이고, 빌드 속도를 향상시키며,
프로젝트의 장기 유지보수성을 보장한다.

### III. 테스트 우선 (Test-First)

**원칙:**
- 핵심 로직은 반드시 테스트를 작성해야 한다 (MUST)
- 최소 70% 코드 커버리지 목표를 유지해야 한다 (MUST)
- API 엔드포인트는 계약 테스트(Contract Test)를 포함해야 한다 (MUST)
- 테스트는 독립적으로 실행 가능해야 한다 (MUST)

**근거:** 에코 서버는 다른 시스템의 테스트 도구로 사용되므로, 자체 안정성과 신뢰성이
필수적이다. 테스트는 리팩터링 안전성을 보장한다.

### IV. 성능과 응답성 (Performance & Responsiveness)

**원칙:**
- 모든 API 응답은 3초 이내에 완료되어야 한다 (MUST)
- WebSocket 연결은 100ms 이내에 수락되어야 한다 (MUST)
- 로깅은 비동기로 처리하여 응답 시간에 영향을 주지 않아야 한다 (MUST)
- 대시보드는 실시간으로 업데이트되어야 한다 (latency < 500ms) (MUST)

**근거:** 사용자 경험의 핵심은 빠른 피드백이다. 개발 도구로서의 가치는 즉각적인
응답성에 달려 있다.

### V. 관찰 가능성 (Observability)

**원칙:**
- 모든 Request/Response는 로깅되어야 한다 (MUST)
- 연결 상태 변화는 추적 가능해야 한다 (MUST)
- 에러는 구조화된 형식으로 기록되어야 한다 (MUST)
- 대시보드를 통해 실시간 모니터링이 가능해야 한다 (MUST)

**근거:** 에코 서버의 주요 목적은 디버깅과 테스트 지원이다. 완전한 관찰 가능성은
사용자가 시스템 동작을 이해하고 문제를 진단하는 데 필수적이다.

## 기술 제약사항

### 기술 스택
- **런타임**: Node.js (LTS 버전)
- **백엔드 프레임워크**: Express.js
- **WebSocket**: ws 라이브러리
- **프론트엔드**: React (대시보드)
- **테스트 프레임워크**: Jest, Supertest

### API 설계
- RESTful 원칙 준수
- JSON 형식의 요청/응답
- 적절한 HTTP 상태 코드 사용
- 에러 응답 표준화

### 보안
- 입력 검증은 필수 (MUST)
- CORS 설정 명시적 정의 필요 (MUST)
- 민감 정보 로깅 금지 (MUST NOT)

## 개발 워크플로우

### 기능 개발 프로세스
1. **명세 작성**: `/speckit.specify` 명령으로 기능 명세 생성
2. **계획 수립**: `/speckit.plan` 명령으로 구현 계획 생성
3. **작업 분해**: `/speckit.tasks` 명령으로 작업 목록 생성
4. **구현**: `/speckit.implement` 명령으로 작업 실행
5. **검증**: `/speckit.analyze` 명령으로 일관성 검증

### 코드 리뷰 기준
- 헌법 원칙 준수 여부 확인 (MUST)
- 테스트 커버리지 70% 이상 확인 (MUST)
- 응답 시간 목표 달성 여부 확인 (MUST)
- 의존성 추가 시 근거 확인 (MUST)

### 커밋 메시지
- 한국어로 작성
- 변경 사항의 '왜'에 초점
- 형식: `<타입>: <설명>`
  - 타입 예시: feat, fix, refactor, test, docs

## Governance

### 헌법 우선순위
- 이 헌법은 모든 개발 관행보다 우선한다 (MUST)
- 헌법과 충돌하는 요구사항은 거부되거나 헌법 개정이 필요하다 (MUST)
- 모든 PR과 코드 리뷰는 헌법 준수를 검증해야 한다 (MUST)

### 개정 절차
- **MAJOR 버전 증가**: 기존 원칙 제거 또는 재정의 (하위 호환 불가)
- **MINOR 버전 증가**: 새로운 원칙 추가 또는 섹션 확장
- **PATCH 버전 증가**: 명확화, 문구 수정, 오타 수정

### 개정 요구사항
- 개정 이유 문서화 (MUST)
- 영향 받는 코드와 템플릿 파악 (MUST)
- 마이그레이션 계획 수립 (대규모 변경 시) (MUST)

### 준수 검토
- 새로운 기능 개발 시 Constitution Check 수행 (MUST)
- `/speckit.analyze` 명령으로 정기 검증 수행 (SHOULD)
- 헌법 위반 발견 시 즉시 이슈 등록 (MUST)

### 복잡성 정당화
- 헌법 원칙에 위배되는 복잡한 구현은 명시적 근거 필요 (MUST)
- 더 단순한 대안이 거부된 이유 문서화 필요 (MUST)
- plan.md의 "Complexity Tracking" 섹션에 기록 (MUST)
